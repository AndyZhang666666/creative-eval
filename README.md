## 它解决什么问题

内容团队用 AI 一天能出 200 条片段，但判断质量的人还是那几个。全读一遍要 8 小时，读不完就只能抽查；抽查出来的问题散在聊天记录里，一周后没人记得为什么打回；新版 prompt 到底比旧版好不好，只能靠"感觉顺一点"。

产出量被放大了 100 倍，判断质量的产能没变 —— 这个项目补的是这一环。

## 三个关键产品决策

**一、维度定 5 个，不是 10 个。**
可拆的维度有二三十个（视角、意象、信息密度、悬念留存、付费卡点位置……），但每一个都要把 1/3/5 分的锚点写清楚，否则裁判只能靠感觉。维度越多锚点越难写清、越容易互相重叠，分数看起来精细、实际不可信。最终按「能写清锚点」+「低分能对应到一个具体修改动作」筛出 5 个。砍掉了原创性（没有比较集判不了）、意象文笔（短剧最终是口播和分镜，对成片几乎无影响）、付费卡点（属于编排层问题，单看片段评不了）。

**二、权重不平均。**
`consistency` 给 1.2，因为人设崩了观众直接弃剧，是硬伤；`dialogue` 给 0.8，因为可以靠演员台词功底往回捞一部分。这是判断不是计算，改权重只需要动 `lib/rubric.js` 一个文件。

**三、规则先于模型。**
空输入、<80 字、>6000 字在规则层直接拦掉，不进模型。让 LLM 给一段空白打 3 分是没有意义的 —— 边界问题应该在裁判之前处理掉，顺带省下一次调用。

## 什么失败了，怎么修的

**v1：裁判系统性偏松。**
第一版 prompt 跑完 40 条，出现 **11 条满分（5/5/5/5/5）**，加权总分比人工标注平均高 **+0.38**，其中开场钩子维度偏松 +0.61、对白 +0.56。问题是 prompt 只说了"怎么打分"没说"5 分有多难"。

**修法**：prompt v2 只加了一段打分基准 —— 明确 3 分是「能用、需要一次修改」的合格位置，5 分是「同类里最好的 5%、可以直接进成片」，并要求裁判自问"好在哪个句子"。改动只有这一处，改完重跑同一套样本对比。

**另一个失败：解析器太脆。**
跑第一轮时有 5 条 `parse_error`。看原始输出，两个原因：① 输出被 `max_tokens` 截断在 JSON 中途；② 模型在字符串值里直接用了英文双引号（`"第一句就用"37条消息"来……"`）导致 JSON 非法。两个都不是模型"不会"，是它没把输出当机器读的对象。

修法：`extractJson` 加两层兜底（截断后回退到最后一个完整对象、状态机补转义未转义引号），同时加 `validate()` —— 5 个维度必须都有合法的 1-5 整数分，缺一个就标成 `invalid` 而不是静默填默认值。**宁可暴露失败，也不要让一个坏掉的分数看起来像真的。**

## 已知局限与下一步

- **单裁判、无交叉验证**：目前只有一个模型当裁判。下一步应该是多裁判投票 + 与人工分做区分度分析（哪些维度人机分歧最大）。
- **标注量小**：40 条样本、32 条有人工标注，够验证流程不够统计显著。
- **维度覆盖有限**：目前只覆盖短剧/长文本创作场景，换到广告文案、小说、播客稿需要重写锚点。
- **不做流式输出**：评测是给人看结论的，一边打分一边刷字反而看不清。
- **不做用户系统和数据库**：结果落 JSON 文件，够用。
